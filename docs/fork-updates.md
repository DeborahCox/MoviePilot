# Fork 应用内更新

前端 Fork 的 `Sync upstream (v3)` 每六小时合并前端上游分支；后端工作流随后合并后端上游分支。
两者只执行普通推送。合并冲突或远端同时更新时工作流失败，须人工解决后重试，不会强推。
前端 Fork 分支是构建的唯一来源；镜像构建不会临时修改或 rebase 前端源码。

后端工作流每六小时检查上游最新正式 Release。只有前后端 Fork 分别包含对应上游发布代码、
后端版本声明与上游标签一致时，才使用固定的两个 Fork 提交构建镜像和更新包。针对上游的
插件市场发布快照提交，后端祖先检查使用其父提交；其他发布提交必须直接包含在 Fork 中。
前端 Release 标签尚不存在或尚未合并时，本轮失败，下一轮重试。

更新包使用 `v3.x.y-1`，独立发布提交只修改两个版本声明，不写回 `v3`。同一次构建的前端
`dist.zip` 同时用于镜像和 Release，Release 正文记录后端来源及前端提交。正式 Release 和
标签不可覆盖。若失败留下标签或草稿，需先人工检查并清理或修复，再重试；不会自动覆盖。
自动流程目前仅支持不带修订后缀的上游 `v3.x.y` 正式标签。

同一上游版本需要发布 Fork 修复时，手动运行工作流并填写尚未使用的 `release_revision`，
例如 `2` 对应 `v3.x.y-2`。前端构建注入完整发布版本，浏览器缓存检查可区分不同修订版；
前端源码的 `package.json` 无须为 Fork 发布修改。未填写时自动发布默认使用 `-1`。

工作流使用最新 `v3` 的 Fork 代码，其中可能包含上游 Release 之后的提交；它不是对上游
Release 源码的精确镜像。应用内更新只替换程序载荷，不替换 Docker 系统组件；系统基线
不满足时仍需更新镜像。运行实例必须先包含指向 Fork 的更新器。
